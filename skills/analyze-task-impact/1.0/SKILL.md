# Анализ задачи и оценка масштаба изменений

## Цель

Понять суть задачи из JIRA и оценить, во сколько файлов проекта выльется её
реализация. На основе оценки выбрать путь разработки:
- малый объём (в пределах порога) → быстрый путь `on_quick_dev`;
- большой объём (больше порога) → спецификационный путь `on_speckit`.

---

## Контракт skill

Skill работает с явно переданными данными и кодовой базой текущего проекта:
- читает carrier-файл `jira-task.json` (или файл, явно указанный в instruction flow-ноды);
- принимает порог `threshold` числом из instruction flow-ноды;
- читает структуру и содержимое кодовой базы только для оценки зоны изменений;
- не читает другие run-артефакты и не угадывает их имена.

### Источник данных о задаче

Источником является `jira-task.json`. Используй из него:
- `summary` — заголовок задачи;
- `description` — описание задачи;
- `comments` — необязательный массив комментариев; если поле отсутствует или массив
  пуст, работай по `summary` и `description`.

Если ни `summary`, ни `description` не заполнены, заверши работу с ошибкой: невозможно
определить суть задачи.

---

## Аргументы

### Из instruction flow-ноды
- `threshold` — целое число файлов, порог выбора пути. Порог определяется так:
  оценка `<= threshold` →
  `on_quick_dev`; оценка `> threshold` → `on_speckit`.

### Carrier-файл
- `jira-task.json` — состояние задачи, полученное скиллом `jira-issues`.

---

## Step 1 — Извлечь суть задачи

Прочитай `jira-task.json` и собери единое понимание задачи:
1. Сформулируй краткую суть задачи своими словами (2–4 предложения) на основе
   `summary`, `description` и `comments`.
2. Выдели явные требования и ограничения из описания и комментариев.
3. Отметь упоминания конкретных сущностей, эндпоинтов, таблиц, модулей, экранов —
   это опоры для оценки затронутых файлов.

Не додумывай требования, которых нет в источниках. Если данных мало — зафиксируй
это в `confidence`.

---

## Step 2 — Исследовать кодовую базу

Исследуй реальный проект в рабочей директории (обязательно):
1. Определи систему сборки и стек: `build.gradle`, `pom.xml`, `package.json`,
   `pyproject.toml`, `go.mod` и т.п.
2. Определи структуру пакетов/модулей и сложившиеся паттерны по слоям
   (контроллеры, сервисы, репозитории, сущности, миграции, фронтенд, тесты, конфиги).
3. Найди файлы, которые с большой вероятностью придётся создать (`Create`) или
   изменить (`Modify`) для реализации задачи.

Оценка должна опираться на реальную структуру кода, а не на догадки.

---

## Step 3 — Оценить затронутые файлы

Построй список предполагаемых изменений:

| Файл | Действие | Слой | Основание |
|------|----------|------|-----------|
| path/to/File | Create/Modify | schema/domain/repository/service/api/test/config/frontend | какое требование ведёт к изменению |

Сгруппируй по слоям. Посчитай **общее число затронутых файлов** — это `estimatedFiles`.

Учитывай сопутствующие изменения: миграции, DTO/мапперы, конфигурация, тесты.
Не завышай искусственно и не пропускай очевидные слои (например, тесты).

---

## Step 4 — Выбрать путь (route)

Сравни `estimatedFiles` с порогом `threshold`:
- `estimatedFiles <= threshold` → `route = "on_quick_dev"` (малый объём, быстрый путь);
- `estimatedFiles > threshold` → `route = "on_speckit"` (большой объём, спецификационный путь).

Граничный случай: ровно `threshold` файлов считается малым объёмом → `on_quick_dev`.

---

## Step 5 — Записать результат

Сохрани анализ в `impact-analysis.md` (или файл, явно указанный в instruction).

Формат `impact-analysis.md`:

```markdown
# Анализ задачи и оценка масштаба

## Суть задачи
<краткая формулировка из summary + description + comments>

## Требования и ограничения
- <требование 1>
- <требование 2>

## Предполагаемые изменения
| Файл | Действие | Слой | Основание |
|------|----------|------|-----------|
| ... | Create/Modify | ... | ... |

## Оценка масштаба
- estimatedFiles: <N>
- threshold: <T>
- route: <on_quick_dev | on_speckit>
- confidence: <high | medium | low>
- comment: <краткое пояснение выбора и уровня уверенности>
```

### Заполнение step-summary.json (обязательно!)

Так как skill используется в AI-ноде с dynamic routing, обязательно запиши в
`step-summary.json` поля:

```json
{
  "route": "on_quick_dev",
  "estimatedFiles": 7,
  "threshold": 10,
  "confidence": "medium",
  "actions": ["прочитал jira-task.json", "исследовал кодовую базу", "оценил затронутые файлы"],
  "reasoning": "краткое обоснование выбранного пути"
}
```

Поле `route` обязательно и должно принимать одно из значений: `"on_quick_dev"` или
`"on_speckit"`. Без корректного `route` flow не сможет выбрать ветку.

---

## Constraints

- Не изменяй кодовую базу — этот skill только анализирует и оценивает.
- Не пиши код реализации и не создавай артефакты, кроме `impact-analysis.md`.
- Не додумывай требования, которых нет в `summary`/`description`/`comments`.
- Оценка числа файлов обязана опираться на исследование реального проекта.
- Всегда записывай `route` в `step-summary.json` — без него выбор ветки невозможен.
- Путь выбирается строго по порогу: `<= threshold` → `on_quick_dev`, `> threshold` → `on_speckit`.
